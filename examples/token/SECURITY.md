# 예제 1 보안 노트 — `FixedSupplyToken`

## 위협 모델 요약

이 컨트랙트는 **사용자 자금을 보관하지 않는다.** 잔액 소유권 기록만
관리하므로 공격 표면은 표준 ERC-20 그 자체다. 업그레이드, 소유자,
일시정지, 블랙리스트 진입점이 모두 부재라 그런 권한 남용 경로도 없다
(반대로, 배포된 코드의 결함도 영원히 고칠 수 없다 — 아래 "잔여 위험").

## 감사 결과(F-01..F-08, contracts-audit-2026-10-05) 매핑

| 항목 | 이 예제와의 관계 |
|---|---|
| **F-01** 예치 재진입 | **해당 없음.** 예치·출금 기능이 없고 ERC-20 transfer는 수신자 콜백을 호출하지 않는다. 이 토큰을 *받는* 컨트랙트(마켓, 스테이킹)는 각자 nonReentrant + 상태 선행을 적용한다 — 예제 3 이하 참조. |
| **F-02** fee-on-transfer 펀딩 좌초 | **해당 없음.** 잔액 산술이 표준(`from -= amount; to += amount`). 이 토큰은 절대 수수료를 떼지 않으므로 SafeToken의 `pullExact` 가정을 만족한다. |
| **F-03** 무코드·불성실 토큰 | 이 토큰을 받는 쪽의 문제. 이 컨트랙트는 배포 시점에 코드를 가지며 transfer가 정직하므로 예제 전반의 `SafeToken` 가드와 양립한다. |
| **F-04** 무한 view DoS | **해당 없음.** 뷰가 `balanceOf`/`totalSupply`뿐이고 전부 O(1). 순회·집계 뷰가 없다. |
| **F-05** EIP-7702 원본 키 | 무관. 위임을 다루지 않는다. |
| **F-06** 단일 registrar 키 | 무관 (이름 서비스 이슈). |
| **F-07** 오픈 로그 ≠ 승인 | `Transfer`/`Approval` 이벤트는 표준 파싱용. 누구나 이벤트를 읽을 수 있지만 그것이 어떤 승인도 아니다 — manifest의 `contracts[]` 선언이 지갑의 신뢰 힌트 전부다. |
| **F-08** randomness 에포크 | 무관. 무작위성을 사용하지 않는다. |

## 이 예제 고유 위험과 완화

| 위험 | 완화 |
|---|---|
| 초기 수령인 주소 오타 — 공급 전량이 잘못된 주소로 | 배포 전 주소 재확인 + 소액 테스트넷 배포 먼저 (chain 7780). 생성자에 `ZeroRecipient` 가드만 있으며 주소 유효성은 확인하지 못한다. |
| permit 서명 재사용 | EIP-2611 논스로 1회성. `deadline`을 반드시 짧게 서명할 것 — 만료 없는 서명은 장기 위임이 된다. |
| 무한 approve 관례 (`type(uint256).max`) | OZ v5 기본은 **유한** 허용량(소진 후 0). 프론트엔드는 필요 금액만 승인하도록 권장한다 (`apps/token/index.html` 참조). |
| 배포 후 결함 불변 | 업그레이드 경로 부재는 의도된 선택. 결함이 발견되면 새 토큰 배포 + 마이그레이션이 유일한 경로다. 단, 기존 보유자 이주는 강제할 수 없다. |

## 퍼즈·불변식

자금 보관 컨트랙트가 아니므로 invariant suite는 보존 불변식 하나로
충분하다 — `test_fuzz_supplyConserved` (25 스텝 × 4 주소 랜덤 이체 후
Σ잔액 == totalSupply). CI 1000 runs / 로컬 심층 5000 runs.
