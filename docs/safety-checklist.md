# 안전 체크리스트 — F-01 … F-08 회피 검증

> 예제를 복사해 커스터마이징했다면, 커밋·배포 전에 이 체크리스트를
> 처음부터 끝까지 통과시켜라. 17개 예제는 아래 8개 위협 클래스를 전부
> 회피하도록 설계됐고, 각 예제의 `SECURITY.md`는 이 표의 근거를
> 예제별로 문서화한다. **커스터마이징은 회피를 해제하는 가장 쉬운
> 방법이다.**

## 위협 클래스 8종

### F-01 — 재진입 (reentrancy)

외부 호출(`call{value}`)이 상태 변경 뒤에 오면, 수신 컨트랙트가
다시 들어와 같은 인출을 반복한다.

- [ ] 이체·정산 함수는 CEI 순서: **검사 → 상태 변경(delete 포함) →
  이벤트 → 외부 전송**
- [ ] `ReentrancyGuard`(또는 동등)가 자금 이동 함수에 붙어 있다
- [ ] **delete가 이벤트·전송보다 먼저**다 — 재진입 시 "대상 부재"로 죽는다
- [ ] pull 지급이 필요한 곳은 push 대신 잔액 매핑 + 별도 인출

### F-02 — 수수료-온-전송 토큰 (fee-on-transfer)

ERC-20 `transferFrom`으로 A가 들어왔는데 실제 도착은 A−f. 잔액
계산이 어긋난다.

- [ ] 예제들은 native만 다룬다 — **토큰을 추가했다면** 전송 전후
  `balanceOf` 차이로 정산하고, FoT 토큰을 명시적으로 거부하라
- [ ] 스왑·매입에서 "들어온 양"을 `msg.value`/차액 측정에서 얻는다

### F-03 — 무코드 토큰 (balance-tracking token)

`receive()`를 열어두고 잔액 매핑을 따로 유지하면, 그 컨트랙트는
사실상 관리되지 않는 토큰이다.

- [ ] 자금을 받는 컨트랙트의 `receive()`는 **revert** (지불은 지정된
  함수 호출로만)
- [ ] 혹은 의도된 경우 문서화 (드롭 풀 충전용 `receive` — 예제 13·15)

### F-04 — 비례 뷰 순회 (proportional-scan views)

사용자 전원을 순회하는 뷰 함수는 호출 비용이 사용자 수에 비례한다.
규모가 커지면 아무도 호출할 수 없다.

- [ ] 사용자 목록을 모으는 뷰가 없다
- [ ] 통계는 이벤트 로그 스캔으로 (합계 슬라라라 필요 시 1개만)
- [ ] 개별 조회는 id/주소 직접 조회만

### F-05 — 7702 위임 계정 (delegated accounts)

EIP-7702로 임의 코드를 깐 계정이 `msg.sender`로 들어온다.
"EOA만 받겠다"는 가정은 성립하지 않는다.

- [ ] 자격 판정이 `msg.sender`의 주소 동등성·잔액으로만 이뤄진다
- [ ] 수신 콜백(`receive`/훅)을 자금 흐름의 전제로 삼지 않는다 —
  **전송은 `call`의 성공 여부만 본다**
- [ ] "사람만 된다"는 특별 경로가 없다 — 계정의 종류가 규칙을 바꾸지
  않는다 (예제 17이 모범)

### F-06 — 단일 registrar 키 (single registrar key)

할당·차단·승인을 하는 관리 키는 그 자체가 실패 지점이자 악의 표면이다.

- [ ] 사용자에게서 뭔가를 빼앗거나 재배치할 수 있는 키가 없다
- [ ] 운영 키의 권한은 **진입 차단(brake)과 인출(본인 것)** 뿐
- [ ] 자격·승인의 원본이 온체인 규칙(머클 루트, 시스템 상태, 기한)에
  있고, 키의 재량이 아니다

### F-07 — 오픈 로그 ≠ 승인 (open logs are not approval)

이벤트는 누구나 남길 수 있는 영수증이지 시스템의 승인이 아니다.

- [ ] 로그를 읽고 "승인됐다"고 판단하는 로직이 없다
- [ ] 앱 스토어·프론트가 로그를 전시할 때 **서사가 아니라 사실만**
  보여준다 ("해시가 등록됐다" ≠ "품질이 좋다" — 예제 17 참고)
- [ ] 프론트가 검증 없이 로그의 문자열을 실행에 쓰지 않는다

### F-08 — 무작위성 (on-chain randomness)

`block.timestamp`·`blockhash`·난수는 검증자·빌더가 조작할 수 있다.

- [ ] 추첨·당첨은 **커밋-리빌**(예제 14) 또는 시스템 VRF를 쓴다
- [ ] 마감 경쟁이 있으면 기한을 넉넉히 (예제 17의 `DeliveryTooLate`
  경계 참고)
- [ ] 무작위성이 필요 없는 구조(선착순, 머클 증명)로 바꿀 수 있는지
  먼저 검토

## 배포 전 최종 점검

- [ ] `FOUNDRY_FUZZ_RUNS=5000 forge test` — 자금 보유 불변식 전 수 통과
- [ ] 각 예제 `SECURITY.md`의 불변식이 커스터마이징 후에도 성립
- [ ] `forge coverage` — 자금 경로 100%에 가깝게
- [ ] brake 걸었을 때 **탈출 경로가 열려 있는지** (진입만 막히는지)
- [ ] 잔액이 갇히는 경로가 하나도 없는지 — "아무도 안 눌러도 되는
  상태에서 돈이 컨트랙트에 남는 경우"를 나열하고 각각 출구 확인
- [ ] 프론트(`apps/`)가 체인 ID(0x1e64)를 검증하는지
- [ ] `manifest.json`이 스키마 검증을 통과하는지
  (`python3 templates/publish/validate-manifests.py`)
