# 예제 12 — 올오어낫싱 크라우드펀드

> ⚠️ **법적 고지 — 공개 배포 전 법률 검토 필수.** 대중에게서 자금을
> 모아 수혜자에게 인도한다. 관할에 따라 이는 기부 모금·전자자금모집
> 규제, 나아가 수익 약속 여부에 따라 증권 규제의 대상이 될 수 있다
> (FUNDRAISING ADJACENT 영역). 수익 배분·이자·토큰 보상을 붙이는
> 순간 규제 노출이 급격히 커진다. 이 예제는 코드 견본이며 법률
> 자문이 아니다.

마감까지 목표를 채우면 전액이 수혜자에게, 못 채우면 전원이 전액
환불받는다. 중간 지점은 없다 — 그래서 회계가 단순하다.

| | 올오어낫싱 (이 예제) | 킵잇올(못 채워도 수령) |
|---|---|---|
| 목표 미달 시 | 전원 전액 환불 | 수혜자가 잔액 수령 |
| 기여 슬롯 | **실패 시 소거** — 영구 상태 0 | 전원 영구 보존 |
| 환불 회계 | 슬롯이 곧 원장 — 산수 없음 | 불필요 (대신 기여자 분쟁) |
| 기여자 심리 | "목표를 안 채우면 돌려받는다" | "이 프로젝트는 부분도 받는다" |
| 규제 노출 | 낮음 (구매·후원에 가까움) | 높음 (수령 확정 시 의무 발생) |

**핵심 설계 — 일시적 상태(temporary state).** 기여자 슬롯은 환불
회계에 필수다: "누가 얼마 냈는가"를 잔액이나 이벤트에서 유도하면
안 된다. 다만 이 예제는 그 슬롯을 **캠페인이 실패할 때 지운다**:

```
성공: raised ≥ goal → 슬롯은 영구 남는다 (출처 증명 — 국고 회계)
실패: 마감 + 미달   → 환불이 슬롯을 delete — 상태는 정리된다
```

1,000명이 모였다 실패해도, 마지막 환불자가 떠난 시점의 영구 상태는
**0에 수렴한다**. 유료 상태 체인에서 "실패한 캠페인의 흔적"까지
영원히 내는 것은 낭비다 — 환불이 청소를 대신한다.

**판정은 스칼라 하나.** 목표 달성 여부는 `raised >= goal` 비교 한
번이다(F-04). 기여자 목록을 순회하거나 합계를 재계산하는 뷰가
없다 — 어느 시점이든 O(1)에 판정된다.

## 조기 달성과 초과 기여

- **조기 달성**: 목표를 채우는 순간 `contribute`는 막히고
  (`AlreadyFunded`) `withdraw`는 마감 전이라도 연다. 기여자는
  "달성 = 성공"을 이미 알므로 마감까지 기다릴 이유가 없다.
- **초과 기여**: 마지막 기여가 목표를 넘어도 전액 수용한다. 초과분은
  후원 — 초과분 비례 환불은 회계를 복잡하게 하고(부분 성공)
  all-or-nothing 정신이 아니다. 대신 **달성 후에는 더 못 넣게
  막는다**(초과 기여는 의도적인 마지막 한 방에만 일어난다).
- **환불은 셀프 클레임**: 키퍼가 일괄 환불하지 않는다. 각자
  `refund()` — 운영자에게 일괄 환불 가스·재진입 표면을 주지
  않는다. 마감 후 언제든, brake가 걸려도 호출할 수 있다.

## 함수표

### `AllOrNothingCrowdfund` (guardian, beneficiary, goal, durationSec)

| 함수 | 호출자 | brake | 효과 |
|---|---|---|---|
| `contribute()` (payable) | 누구나 | 진입 차단 | 기여 누적. 마감 후·달성 후 거부 |
| `refund()` | 기여자 본인 | **무관 (탈출)** | 실패 시 전액 환불 — 슬롯 소거 |
| `withdraw()` | **누구나** | **무관 (탈출)** | 성공 시 전액을 beneficiary에게 인도 (1회) |
| `state()` | 뷰 | — | 0 진행중 / 1 성공 / 2 실패 / 3 인도 완료 |

`beneficiary`는 배포 시 고정이다 — 인도는 permissionless라 누구나
트리거할 수 있지만 수령인은 바뀌지 않는다. `receive()`는 거부해
회계 밖 송금을 막는다.

## 배포

```bash
forge create src/crowdfund/AllOrNothingCrowdfund.sol:AllOrNothingCrowdfund \
  --constructor-args $GUARDIAN $BENEFICIARY 10000000000000000000 2592000 \
  --rpc-url $RPC --private-key $DEPLOYER
# goal 10 EAST, duration 2_592_000초(30일)
```

- `guardian`: 비상 제동(신규 기여 차단만) — 하드웨어 지갑 권장
- `beneficiary`: 성공 시 수령인 — **배포 후 변경 불가**. 컨트랙트
  지갑이라면 native를 받을 수 있어야 한다(receive 있음).
- `goal`/`durationSec`: 배포 시 고정. 목표·마감 변경은 새 캠페인
  배포로만 — 진행 중 캠페인의 규칙을 바꾸는 키를 만들지 않는다.

상태 비용 요약 (측정 환경·전체 수치는 [GAS.md](GAS.md)):

|---|---:|

## 커스터마이징 경고

- **부분 달성(예: 50% 넘으면 수령)**을 붙이는 순간 환불 회계에
  비례 배분이 필요해진다 — 스칼라 판정의 이점이 사라진다. 그 갈래는
  예제 9(에스크로)와 조합해 별도 캠페인으로 만들어라.
- **마감 연장 키**를 만들지 마라. "조금만 더 모으면 되는데"는
  기여자가 이미 낸 돈의 규칙을 사후에 바꾼다. 연장은 새 캠페인.
- **일괄 환불 함수**를 추가하고 싶어질 것이다 — 하지 마라. 반복
  환불은 가스를 운영자에게, 실패 처리(수신 거부 기여자)의 정책을
  컨트랙트에 강요한다. 셀프 클레임이 정답이다.
- **초과분 비례 환불**은 "성공"의 정의를 흐린다 — 올오어낫싱을
  유지한다면 초과분은 명시적 후원이어야 한다 (프론트에서 안내).
