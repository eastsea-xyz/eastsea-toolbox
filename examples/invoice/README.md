# 예제 16 — Tide Ledger · 번호 인보이스 장부

> [!WARNING]
> **공개 배포 전 법률 검토 필수.** 대금 결제 수단의 사업자 의무
> (세금계산서·전자상거래법·지역 소비자 보호)는 관할별로 다르다.
> 수익·가격 약속, 코인 리워드 추천 구조는 포함하지 않는다
> (docs/legal-notes.md).

프리랜서·소규모 업체가 온체인으로 **번호가 붙은 고정액 청구서**를
발행하고, 고객이 정확한 금액을 결제하면 즉시 정산되는 원장이다.
에스크로(예제 9)가 양측 사이의 **조건부 중개**라면, 인보이스는
단방향 **청구·결제**다 — 조건도 중개도 없다.

```
payee:    issue(amount, payBy, memo) ──▶ 청구서 #N 발행 (슬롯 1개)
고객:     settle(N){value: amount}  ──▶ 즉시 정산 + 슬롯 반납
payee:    void(N)                    ──▶ 폐기 (슬롯 반납)
누구나:  purge(N)  (만료 후)         ──▶ 죽은 청구서 슬롯 반납
```

## 왜 이 구조인가 — 결제된 청구서는 존재하지 않는다

유료 상태 체인에서 인보이스 원장의 함정은 "결제 이력이 영구히
쌓인다"는 직관이다. 결제 완료를 `paid` 플래그로 표시하면 슬롯은
영원히 남는다 — 1년에 1만 건을 발행하면 1만 슬롯(≈100만u)이
장부에 눌어붙는다.

이 예제는 반대로 간다: **settle은 매핑 원소를 `delete`한 뒤 전송한다
(CEI)**. 결제된 청구서는 존재하지 않는다.

- **이중결제 원천 차단** — 이미 결제한 청구서에 다시 `settle`을
  보내면 `UnknownInvoice`다. paid 비트를 읽고 거부하는 것이
  아니라, 질문 자체가 성립하지 않는다.
- **영수증은 이벤트와 누계** — 건별 증빙은 `Settled(id, payer,
  amount)` 로그, 사업 실적은 `totalSettled` 스칼라 하나. "이
  청구서 결제됐나?"의 온체인 답은 "그런 청구서가 없다" — 부재로
  표현되는 진실이다 (F-07의 역발상).
- **폐기도 반납이다** — `void`의 gas는 2,895뿐이다. 슬롯을 사는
  것이 아니라 되돌려주는 것이라 gas 환급이 붙는다.

### 상태 수명 요약

| 사건 | 슬롯 변화 | 상태 |
|---|---|---:|
| 발행 | +1 (amount+due 팩) | 108u |
| 결제 | −1 청구서, +최초 1 누계 | 106u (첫 회만) |
| 폐기/만료 반납 | −1 | **4u** |
| 누계(totalSettled) | 첫 정산 1회 | 1슬롯 영구 |

미결제 청구서만 슬롯을 점유한다 — 대기 중인 돈의 양과 상태의
양이 일치한다. 발행-결제 주기가 짧고 규칙적인 사업체(역방향:
주간 정기 결제는 예제 10)일수록 장부의 순영구 상태가 0에 수렴한다.

## 설계 결정

### 1. 메모는 로그에만

`issue`의 `memo`(품목·주문번호)는 스토리지에 저장되지 않고
`Issued` 이벤트의 페이로드로만 남는다. 슬롯은 `amount + due` 팩
하나 — 문자열 1바이트가 영구 1u짜리 되는 것을 피한다(예제 15와
같은 원칙).

### 2. 만료는 가격 보장의 종료

`due` 이후 `settle`은 거부된다(`InvoiceExpired`) — 만료된 가격을
강제로 받아들이게 하지 않는다. payee는 재발행하면 된다. 만료된
미결제 청구서는 누구나 `purge`로 슬롯을 반납할 수 있다(상태 위생).

### 3. payee는 수취인이지 관리자가 아니다 (F-06)

payee가 할 수 있는 일은 발행과 폐기뿐이다. 금액 수정 키, 마감
연장 키, 재발행 강제 키 — 모두 없다. 잘못 발행했으면 `void`하고
새 청구서를 낸다. `totalSettled`는 내림 불가능한 순누계라 사업
실적 증명이 된다.

### 4. brake는 발행만 막는다

`SimpleBrake`로 신규 발행을 멈출 수 있다(운영 중단·계약 분쟁).
이미 발행된 청구서의 결제·폐기·반납은 항상 열려 있다 — 장부를
멈춰도 돈의 출구를 막지 않는다.

## 라이프사이클 사용법

```bash
# 발행 — 청구서 #1, 0.5 EAST, 14일 안에 결제, 메모는 로그로
cast send $BOOK 'issue(uint128,uint48,string)' 500000000000000000 1209600 "logo design v2"

# 결제 — 금액은 정확히 (초과·미달·밖 송금 모두 거부)
cast send $BOOK 'settle(uint256)' 1 --value 0.5ether

# 조회 — 미결제만 보인다 (결제된 청구서는 부재)
cast call $BOOK 'invoices(uint256)' 1

# 실적 — 이 장부가 정산한 누계
cast call $BOOK 'totalSettled()'
```

## 커스터마이징 경고

- **금액 수정 금지**: 발행 후 금액을 바꾸는 키를 추가하는 순간
  "고객이 승인한 금액"과 "결제 시점 금액"이 갈라진다. 폐기 후
  재발행이 유일한 수정 경로다.
- **부분 결제 금지**: "얼마든 넣고 채워지면 결제" 구조는 청구서를
  예치 컨트랙트로 바꾼다 — 잔액 원장·환불 경로가 새로 필요하다.
  그 요구라면 예제 9(escrow) 설계로 가라.
- **due 연장 금지**: 마감 연장은 "이미 못 받는 줄 안 고객"에게
  다시 열어주는 권한이다. 재발행으로 대체하라.
