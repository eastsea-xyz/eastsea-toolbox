# 예제 16 보안 — Tide Ledger (인보이스 장부)

## 위협 클래스 회피 (F-01 … F-08)

| 클래스 | 이 예제의 회피 |
|---|---|
| **F-01** 재진입 | `settle` CEI — `delete invoices[id]`·누계·이벤트가 전부 전송보다 앞. 재진입 시 청구서는 이미 없다(`UnknownInvoice`). `nonReentrant` 이중 안전. |
| **F-02** 수수료-온-전송 토큰 | native AETH만 다룬다. |
| **F-03** 무코드 토큰 | 토큰 없음. `receive()`는 `PaymentNotAllowed`로 거부 — 결제는 `settle(id)`뿐이라 잔액 추적 토큰이 될 수 없다. |
| **F-04** 비례 뷰 순회 | 순회 없음. 청구서는 id 직접 조회, 실적은 스칼라. |
| **F-05** 7702 위임 | 결제자 비교는 `msg.value`와 청구서 금액뿐 — 위임 EOA 동일. |
| **F-06** 단일 registrar | payee는 수취인이지 관리자가 아니다. 금액 수정·마감 연장·강제 폐기 키가 없다. payee·guardian 외에 어떤 권한 필드도 존재하지 않는다. |
| **F-07** 오픈 로그 ≠ 승인 | `Settled` 이벤트는 영수증이지만 진실은 `totalSettled` 스칼라와 슬롯 **부재**다. 위조 로그로는 재결제·환불 청구 어느 쪽도 만들 수 없다. |
| **F-08** 무작위성 | 없음. |

## brake 범위

`issue`(진입 — 새 청구 권리 생성)만 `whenEntryOpen`으로 차단된다.
`settle`·`void`·`purge`(탈출·반납)는 항상 개방 — brake를 걸어도
이미 발행된 청구서의 돈은 고객·payee 어느 쪽이든 갇히지 않는다.

## 불변식 (테스트로 검증)

- **I1 — 정확한 금액만**: `msg.value != amount`면 거부 (초과·미달
  모두, `WrongAmount`).
- **I2 — 이중결제 부재**: 결제된 id의 재결제는 `UnknownInvoice`.
  paid 플래그가 아니라 슬롯 삭제로 달성된다.
- **I3 — 원장-잔액 일치**: `totalSettled == 결제된 청구서 금액의
  합 == payee 잔액 증가` (fuzz: 발행 n건 × 결제/폐기/방치 분기).
- **I4 — 폐기·반납은 정산 아님**: `void`/`purge`는 `totalSettled`를
  건드리지 않는다 (방치분만 슬롯에 남는다, fuzz).

## 고유 위험

| 위험 | 성격 | 완화 |
|---|---|---|
| **잘못된 금액 발행** | payee의 입력 실수. | 즉시 `void` → 재발행. 슬롯은 반납되고 영구 흔적은 `Voided` 로그뿐. |
| **만료 직전 결제 경쟁** | `due` 경계에서의 결제는 블록 타임스탬프로 판정 — 고객이 "직전에 보냈다"고 주장해도 체인 기준이다. | `InvoiceExpired(at, due)`가 근거를 제공한다. 마감은 넉넉히. |
| **purge 가스 낭비 (griefing)** | 누구나 만료 청구서를 반납할 수 있지만 자기 가스를 쓸 뿐 남에게 손해가 없다 — payee의 슬롯이 사라져 오히려 이득. | 공격 면 없음 (반납은 멱등). |
| **payee가 EOA가 아닌 컨트랙트** | `settle`의 전송이 실패하면(`SettleTransferFailed`) 해당 청구서의 결제가 아예 불가능해진다. | payee는 네이티브 수신 가능 주소여야 한다. 배포 전 확인 — 실패해도 자금은 발신자에게 롤백된다(갇히지 않는다). |
| **memo 위조 (F-07 응용)** | `Issued` 로그의 memo는 발행자 서명이나 무결성이 없다. | memo는 표시용 서사다 — 정산 금액·대상의 진실은 슬롯과 `totalSettled`. 프론트는 memo를 검증 문구로 쓰지 않는다. |
| **청구서 번호 예측** | id는 순차 증가 — 경쟁자가 거래량을 대략 추정할 수 있다. | 공개 원장의 본질. 비밀이 필요하면 이 패턴이 아니다. |

## CEI 세부 — delete가 먼저다

`settle`의 효과 순서: (1) 슬롯 읽기·검사 (2) `delete invoices[id]`
(3) 누계·이벤트 (4) 전송. 악의적 payer가 전송 콜백(컨트랙트 지갑)으로
재진입해도 청구서는 이미 없다 — 재진입 경로가 상태를 겹쳐 쓸 여지가
없다. `nonReentrant`는 같은 보장의 두 번째 자물쇠다.

## 남는 신뢰 가정

- 블록 타임스탬프가 마감 판정의 기준이다 (검증자 왜곡 폭은
  수 초 — 14일 마감에 무의미).
- payee가 `void`를 남발해 결제 직전 청구서를 취소하는 것은
  **악의가 아니라 권리**다 — 고객의 보호는 `Settled`가 확정된
  이후부터다 (확정 정산은 번복 불가).
