# 예제 15 보안 — Reef Drop (이름 자격 드롭)

## 위협 클래스 회피 (F-01 … F-08)

| 클래스 | 이 예제의 회피 |
|---|---|
| **F-01** 재진입 | `claim`/`sweep` `nonReentrant` + CEI — `claimed` 비트·`claimCount`·이벤트가 모두 전송보다 앞. 호출 대상은 EOA·컨트랙트 무관하게 지급 후 재진입할 상태가 없다. |
| **F-02** 수수료-온-전송 토큰 | native AETH만 다룬다. ERC-20 경로 자체가 없다. |
| **F-03** 무코드 토큰 | 토큰을 발행하지 않는다. `receive()`는 풀 충전일 뿐 잔액 추적 토큰이 아니다. |
| **F-04** 비례 뷰 순회 | 순회가 없다. 자격은 외부 뷰 1회(`reverseOf`), 예산 조회는 스칼라(`claimCount`) 상수 시간. |
| **F-05** 7702 위임 | 위임 EOA도 동일하게 취급 — 비교하는 것은 `msg.sender`의 시스템 reverse 기록뿐. 위임 대상 컨트랙트의 코드는 영향 없다. |
| **F-06** 단일 registrar | registrar가 없다. `names`·`distributor`·`deadline`·`dropAmount` 전부 immutable — 배포 후 개입 가능한 필드가 없다. distributor는 마감 후 잔여 수령인일 뿐 키가 아니다. |
| **F-07** 오픈 로그 ≠ 승인 | `Claimed` 이벤트가 자격을 증명하지 않는다 — 진실은 `claimed` 매핑. 이벤트를 흉내 낸 계정은 이미 `claimed=true`인 주소뿐이다. |
| **F-08** 무작위성 | 무작위성이 없다. 자격 배정은 이름 서비스 등록이라는 결정론적 사실이다. |

## brake가 없는 이유

진입(자금·권리 유입)이 존재하지 않는다 — 자격은 외부 시스템의
상태이고 이 컨트랙트의 정책은 배포 시 전부 immutable로 고정됐다.
남은 두 함수 `claim`(탈출)과 `sweep`(탈출)은 막으면 사용자 자금이
갇힌다. 예제 13(airdrop)과 동일한 논리다.

## 불변식 (테스트로 검증)

- **I1 — 이름 없는 계정은 0원**: `reverseOf == ""`인 주소의 `claim`은
  전원 revert (fuzz: 미등록 계정 전수 검증).
- **I2 — 이름 보유자는 정확히 DROP**: 지급액은 항상
  `dropAmount`와 정확히 같다 (fuzz 보존).
- **I3 — 원장-스칼라 일치**: `claimCount == 성공한 청구 수`,
  `balance == 충전 총액 − claimCount × dropAmount` (fuzz).
- **I4 — 마감 후 전액 인도**: `sweep` 후 컨트랙트 잔액은 0,
  잔여 전액이 distributor에게 (경계 `<=`/`>` 분리 검증).

## 자격 위임의 정확성 — mock 없는 통합 테스트

자격 판정을 시스템에 위임했으므로 **시스템의 실제 정확성** 위에서
검증해야 한다. 테스트는 `EastSeaNames`를 mock 하지 않고 진짜를
배포해 commit → (60초) → register → setAddr → setReverse 전체
절차로 이름을 만든다. mock은 "내가 짜 믿는 reverseOf"만 검증한다.

검증된 위임 동작 3가지:

1. **만료**: 등록 만료 + 유예(`expires + GRACE`) 도달 순간
   `reverseOf`가 조용해지고(`""`) 자격이 소멸한다 — drop은 만료를
   자체 관리하지 않는다.
2. **addr 이동**: 소유자가 이름의 주소를 옮기면 시스템이 reverse를
   능동 삭제한다 — 스푸핑된 역방향 주장이 남을 수 없다.
3. **이전**: 2단계 이전(`transferPropose`/`transferAccept`) 후 새
   소유자가 `addr`+`reverse`를 세우면 자격도 이동한다. 자격의
   주체는 "지금 그 이름을 대표하는 계정"이다.

## 고유 위험

| 위험 | 성격 | 완화 |
|---|---|---|
| **가명 계정 (Sybil)** | primary name은 계정당 1개지만 계정 자체를 여러 개 만들 수 있다 (이름당 소각 0.1 AETH). 이 게이트는 "시스템 등록 계정"까지다. | 1인 1회가 요건이면 자격 기준에 추가 증명이 필요하다 — 설계 변경. README "커스터마이징 경고" 참고. |
| **마감 직전 이름 만료** | 청구 창구 끝자락에 이름이 만료되면 그 계정은 못 받는다. | 앱의 잘못이 아니다 — 참가자가 renew를 안 한 것. 배포자는 청구 기간을 이름 잔여 기간보다 짧게 잡는 운영 권고로만 대응한다. |
| **풀 미충전** | `balance < dropAmount`면 정당한 자격자의 claim이 revert된다. | 잃을 것은 없다 (revert일 뿐). 누구나 `receive()`로 충전할 수 있고, 부족분은 마감 후 sweep으로 회수 — 갇히는 경로 없음. |
| **잘못된 names 주소** | 생성자에 잘못된 주소가 들어가면 자격 판정이 엉킨다. | immutable이므로 회복은 마감 후 sweep → 재배포뿐 (예제 13의 루트 오타와 동일한 회복 경로). 배포 스크립트로 주소를 검증하라. |
| **이벤트 위조 (F-07 응용)** | `Claimed(user, name)`을 흉내 낸 로그는 만들 수 있어도 `claimed[user]`를 바꾸지 못한다. | 진실 원천은 매핑 — 프론트는 이벤트만 믹업하는 UI를 만들지 않는다. |

## 남는 신뢰 가정

- 시스템 이름 서비스(`EastSeaNames`)가 무결하다는 가정 위에서
  자격이 정의된다. 시스템은 불변·무소유자이므로 이 가정은 체인
  자체의 가정과 같다.
- `reverseOf`의 external call은 신뢰 경계가 아니라 읽기다 —
  악의적 names는 애초에 배포 시 통제 대상이다 (immutable).
