# 유료 상태 설계 — EastSea 앱의 상태 비용 설계론

> 이 문서는 17개 예제(`examples/`)가 공유하는 설계 원칙의 총결이다. 예제를
> 복사해 커스터마이징할 때 이 문서의 원칙을 어기는 순간, 앱은 성공에
> 비례해 파산하는 구조가 된다.

## 1. 비용 구조 — 상태는 사고다, 로그는 저렴하다

EastSea의 앱 상태는 저장소가 아니라 **점유**다. 대략:

| 항목 | 비용 | 성격 |
|---|---:|---|
| 신규 슬롯 1개 (20,000 gas) | ≈ **100u** | 영구 — 반납 전까지 매 순간 점유 |
| 슬롯 수정 (5,000 gas) | ≈ 25u | 영구 |
| 슬롯 반납 (delete, −4,800 gas) | ≈ −24u | **환급** |
| 이벤트 로그 64B + 데이터 | ≈ 5u | 영구하되 이더리움 수준, 사실상 무료 |

1u = 1e12 wei. 핵심 대비:

- 영수증 문자열 하나를 상태에 저장하면 ≈ 수백 u. **로그에 남기면 ≈ 5u.**
- 완료된 거래를 슬롯으로 남겨두면 100u씩 영구 축적. **delete로 반납하면
  대부분 환급된다.**

그래서 이 툴박스의 제1원칙:

> **문자열과 서사는 로그에, 상태는 진행 중인 돈·권리만, 완결은 delete로.**

## 2. 슬롯의 수명 주기 — 태어나고, 일하고, 반납된다

17개 예제 전부가 같은 슬롯 수명 주기를 따른다:

```
(없음) ──생성──▶ 진행 중 ──완결──▶ (없음, delete)
                     │
                     └── 방치 ──▶ 진행 중 (소유자의 청구를 기다림)
```

- **생성은 진입이다**: 주문·후원·등록이 새 슬롯을 만든다. (`SimpleBrake`의
  `whenEntryOpen`이 막는 지점도 항상 이 진입이다.)
- **완결은 delete다**: 결제·배달·환불·폐기는 슬롯을 지운다. 예제 16
  (invoice)의 `settle`은 paid 플래그 대신 `delete invoices[id]` — "결제된
  청구서는 존재하지 않는다"가 이중결제 방지 그 자체다.
- **방치만이 누적이다**: 유일한 상태 누적 경로는 아무도 완결을 누르지
  않는 것이다. 그래서 각 예제는 방치분을 제3자가 청소할 수 있는 출구
  (`purge`, `sweep`, 마감 후 permissionless 환불)를 갖는다.

### 영구 슬롯은 스칼라만 허용한다

카운터(`orderCount`, `totalSettled`)와 배포 시 immutable은 영구 슬롯으로
인정된다. 1개짜리 스칼라는 프로그램 수명 내내 고정 비용이기 때문이다.
**사용자별·거래별 영구 슬롯은 설계 실패다.**

## 3. 완결의 세 가지 패턴

예제들이 delete로 도달하는 완결은 세 형태다:

1. **합의 완결** (escrow 9, market 3): 상대방의 명시적 승인이 조건.
   대가 — "승인 대기 중인 돈" 슬롯이 존재 기간만큼 산다.
2. **기한 완결** (invoice 16, vending 17, raffle 14, crowdfund 12):
   기한이 지나면 한쪽이 일방적으로 완결한다. 승인 단계가 없어 대기
   슬롯이 짧고, 잠적한 상대를 기다리는 사람이 없다.
3. **즉시 완결** (invoice의 `settle`, airdrop/names의 `claim`): 입장이
   곧 완결. 슬롯이 존재했다가 사라진다 — 청구형 앱의 이상형.

설계할 때 먼저 묻는다: **"이 슬롯은 누가, 언제, 어떻게 지우는가?"**
답이 없는 슬롯는 만들지 않는다.

## 4. 조회와 통계 — 상태가 아니라 로그에서

- **개별 조회**는 id 직접 조회(`orders[id]`)로만. 사용자 목록 순회 뷰는
  만들지 않는다 (F-04 — 순회 비용이 사용자 수에 비례해 리딩스 필드를
  굶긴다).
- **통계**(총 거래액, 배달률, 참가자 명단)는 이벤트 로그의 영역이다.
  `Delivered` 로그를 세는 것은 무료이고, `totalSettled` 스칼라를 유지하는
  것은 매 건 5,000 gas다. 예제 17은 아예 누계조차 없다.
- 프론트엔드는 `eth_getLogs`로 최근 이력을 조립한다 — `apps/*/index.html`
  의 "최근 이벤트" 탭이 그 예시다.

## 5. 남의 상태를 읽는 것이 최상의 절약이다

예제 15 (names)의 교훈: 자격의 원본이 시스템(EastSeaNames)에 이미
있다면 앱은 그것을 읽기만 한다. 만료·이전·주소 이동의 정직성을 시스템이
무료로 보증하므로 앱의 중복 슬롯은 0개다. **무언가를 저장하기 전에
먼저 "이미 누가 가지고 있나"를 확인하라.**

## 6. 상태 예산 설계법 — 새 예제를 만들 때

1. **슬롯 목록을 먼저 쓴다**: 컨트랙트에서 어떤 매핑·구조체가 살았다
   죽었다 하는지, 수명이 무엇으로 끝나는지 표로 만든다.
2. **최악의 시나리오를 계산한다**: "전건 방치"일 때 1,000건 후 영구
   상태가 얼마인지. (각 예제의 `GAS.md`에 있는 표가 이것이다.)
3. **완결 경로 전부에 gas를 측정한다**: 생성만 싸고 완결이 비싸면
   상태가 쌓인다. delete의 환급(`void` 2,895 gas)이 완결을 오히려
   싸게 만든다.
4. **상태 단위(u)로 보고한다**: gas가 아니라 상태 units로. gas는
   실행 비용, u는 점유 비용 — 둘은 다른 예산이다.

## 7. 반례 — 이렇게 하면 망한다

| 설계 | 왜 망하는가 | 대안 |
|---|---|---|
| 영수증 원문을 `mapping(uint => string)`에 | 건당 수백 u 영구. 성공할수록 비용 증가 | `Issued` 이벤트의 memo 필드 |
| 완료 플래그(`paid=true`) 유지 | 완결이 상태를 늘린다 — 1,000건 = 1,000슬롯 영구 | `delete` — 부재가 곧 완결 (예제 16) |
| 사용자 전원 조회 뷰 | 호출 비용이 사용자 수 비례 (F-04) | id 조회 + 로그 스캔 |
| 관리자가 사용자 목록을 청소 | 청소 키 = 단일 실패 지점 (F-06) | 완결이 곧 이득인 permissionless 청소 (`purge`) |
